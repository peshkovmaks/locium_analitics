# План развития проекта

Дата актуализации: 2026-09-11

## Цель

Превратить дашборд в рабочий центр управления продажами на Wildberries, Ozon и Яндекс Маркете:

- утром показывать, что требует действия;
- в течение дня контролировать отклонения по продажам, рекламе, ценам и остаткам;
- в конце месяца объяснять прибыль, расходы и причины отклонений;
- отделять предварительные оценки от подтвержденных финансовых данных.

## Текущее состояние

Уже реализованы или заложены:

- сбор заказов, продаж, возвратов, остатков, цен, рекламы, финансов и балансов;
- адаптеры для WB, Ozon и Яндекс Маркета;
- расчет выручки, расходов, валовой и чистой прибыли, ДРР;
- юнит-экономика по товарам и площадкам;
- каталог с себестоимостью, минимальной ценой и сопоставлением SKU;
- фоновые синхронизации через Celery;
- дашборд, PDF-отчеты и Telegram-отчеты;
- журнал состояния секций синхронизации.

## Приоритеты

### P0. Доверие к данным и устойчивость

Это обязательный этап перед расширением аналитики.

- Ввести единый resolver SKU через `ProductShopMapping`.
- Использовать его в дашборде, отчетах, Telegram и расчетах себестоимости.
- Добавить показатель покрытия себестоимостью: доля продаж и прибыли, где себестоимость заполнена.
- Исправить историческую синхронизацию: `initial_sync()` должен использовать счетчик секции `orders`, а не отсутствующее поле `sales`.
- Не удалять старый snapshot остатков до успешной загрузки нового.
- Хранить в `SyncLog` период, количество полученных и сохраненных строк, время начала и окончания, признак неполной загрузки.
- Разделить в интерфейсе оценочную и подтвержденную прибыль.
- Добавить тесты для скидок, возвратов, отрицательных финансовых операций, мульти-SKU заказов, распределения расходов и объединения SKU.

**Готово, когда:** повторная синхронизация идемпотентна, ошибки отдельных секций видны пользователю, а расчеты одинаковы в дашборде, отчетах и Telegram.

### P1. Ежедневный центр управления

#### Утренний экран

Добавить блок «Требует внимания» с приоритетом и ссылкой на действие:

- остаток ниже порога;
- прогноз out-of-stock через 3, 7 или 14 дней;
- резкое падение продаж относительно среднего за 7 дней;
- отрицательная или слишком низкая маржа;
- ДРР выше целевого значения;
- цена ниже минимальной;
- продажи без себестоимости;
- магазин или секция не синхронизировались;
- устаревшие финансовые данные.

#### Запасы

Рассчитывать по SKU и площадке:

```text
Дни запаса = Доступный остаток / Средние продажи в день
```

Показывать:

- текущий остаток и товар в пути;
- продажи за 7 и 30 дней;
- средние продажи в день;
- прогноз даты out-of-stock;
- рекомендуемое количество к поставке.

Сначала восстановить остатки WB через Analytics warehouse-remains API. Сейчас `get_stocks()` WB отключен.

#### Реклама

Для кампаний и товаров показывать:

- расходы, заказы и выручку;
- ДРР и стоимость заказа;
- прибыль после рекламы;
- изменение к предыдущему периоду;
- органические и рекламные продажи.

Закрыть пробелы источников:

- Ozon Performance API для фактических рекламных расходов;
- фактические расходы Яндекс Маркета вместо текущего `spend = 0`;
- проверка сопоставления кампаний WB с SKU.

#### Цены

Добавить историю цен и рекомендацию «повысить / оставить / снизить».

Минимальная цена должна учитывать себестоимость, расходы площадки, рекламу и целевую маржу:

```text
Минимальная цена =
(Себестоимость + расходы на единицу)
/ (1 - комиссия - целевая маржа)
```

#### Telegram

Перевести отчеты от простой статистики к списку решений:

- краткие KPI за вчера;
- изменения к среднему и предыдущему периоду;
- топ проблемных товаров;
- новые ошибки синхронизации;
- товары, требующие поставки, изменения цены или рекламного бюджета.

Добавить защиту от повторной отправки одинаковых уведомлений с хранением состояния алерта в БД, а не только в памяти процесса.

**Готово, когда:** утром продавец получает список конкретных действий, а не только набор показателей.

### P1. Месячное закрытие и аналитика

#### Сверка с кабинетами

Добавить отчет «Продажи / Начисления / Выплаты»:

| Показатель | Продажи | Начисления | Выплаты | Расхождение |
|---|---:|---:|---:|---:|
| Выручка | | | | |
| Комиссии | | | | |
| Логистика | | | | |
| Реклама | | | | |
| Возвраты | | | | |
| Прибыль | | | | |

Показывать для каждого периода статус:

- предварительные данные;
- данные с задержкой;
- период закрыт;
- есть расхождения.

Учитывать, что у разных площадок расходы и продажи могут иметь разные даты. Нельзя без маркировки выдавать распределенные расходы как бухгалтерски подтвержденные.

#### Прибыльность ассортимента

Добавить месячную классификацию SKU:

- `A`: высокая прибыль и стабильные продажи;
- `B`: хорошие продажи, но проблемы с маржой, рекламой или возвратами;
- `C`: низкий оборот или отрицательная экономика;
- `D`: нет продаж при замороженном остатке.

Показывать товары, которые:

- дают основной вклад в прибыль;
- создают оборот без прибыли;
- убыточны после всех расходов;
- имеют высокий процент возвратов;
- зависят от одной площадки.

#### Анализ площадок

Сравнивать площадки не только по выручке, но и по:

- чистой прибыли;
- марже;
- ДРР;
- возвратам;
- оборачиваемости запасов;
- доле подтвержденных расходов.

Ключевой показатель:

```text
Доля площадки по прибыли = Прибыль площадки / Прибыль всех площадок
```

#### План-факт

Добавить месячные цели по:

- выручке;
- прибыли;
- марже;
- ДРР;
- заказам;
- возвратам;
- остаткам.

Отчет должен показывать факт, план, отклонение и возможную причину отклонения.

**Готово, когда:** месячный отчет объясняет не только результат, но и причины изменения прибыли.

### P2. Прогнозирование и рекомендации

После накопления минимум 2–3 месяцев качественной истории добавить:

- прогноз продаж и выручки;
- прогноз прибыли;
- сезонность;
- прогноз out-of-stock;
- сценарии изменения цены;
- сценарии изменения рекламного бюджета;
- рекомендации по выводу, перезапуску или расширению ассортимента.

## Приоритетный порядок работ

1. Единое сопоставление SKU и тесты расчетов.
2. Надежность синхронизации и прозрачность качества данных.
3. Остатки WB и прогноз out-of-stock.
4. Реальные рекламные расходы Ozon и Яндекс Маркета.
5. Ежедневный центр действий и полноценные Telegram-алерты.
6. Месячное закрытие и сверка с кабинетами.
7. Анализ прибыльности ассортимента и план-факт.
8. Прогнозирование и автоматические рекомендации.

## Критерии успеха продукта

- Ежедневное решение: продавец за несколько минут понимает, какие товары, площадки и кампании требуют внимания.
- Финансовое решение: в конце месяца можно объяснить расхождение между продажами, начислениями и выплатами.
- Ассортиментное решение: видно, какие SKU развивать, переоценивать, рекламировать или выводить.
- Техническое решение: каждая цифра имеет источник, период, статус полноты и понятное качество данных.
